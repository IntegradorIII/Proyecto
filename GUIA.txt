1. DESCRIPCIÓN GENERAL DEL PROYECTO
----------------------------------------------------------------------
Sistema integral cliente-servidor multiplataforma para la digitalización, 
automatización y gestión de control de asistencia a reuniones, eventos 
y capacitaciones corporativas o institucionales.

El ecosistema está compuesto por 3 módulos principales integrados:
1. Backend (API REST): Desarrollado en Node.js, Express, Sequelize y PostgreSQL.
2. Frontend (Panel Web / Escritorio): Desarrollado en Flutter para gestión 
   administrativa en navegadores web y computadoras de escritorio.
3. mobileCitas (Cliente Móvil / Escáner QR): Desarrollado en Flutter con 
   soporte nativo para cámara (mobile_scanner) enfocado en check-in rápido, 
   escaneo de códigos QR y consulta de convocatorias.

3. ACTORES DEL SISTEMA Y ROLES (RBAC)
----------------------------------------------------------------------
El sistema implementa Control de Acceso Basado en Roles (RBAC):

* Administrador:
  - Control total del sistema y acceso al módulo completo de Usuarios.
  - Gestión de usuarios: Crear, listar, editar y eliminar usuarios.
  - Creación, reprogramación y cancelación de eventos/reuniones.
  - Convocatoria de participantes a eventos.
  - Registro de asistencia manual (presente, tardío, ausente).
  - Consulta y exportación de reportes de asistencia con métricas consolidadas.

* Operador:
  - Gestión operativa del día a día.
  - Creación, reprogramación y eliminación de eventos.
  - Convocatoria de participantes a eventos.
  - Registro de asistencia manual para miembros e invitados.
  - Consulta general de eventos y participantes convocados.

* Miembro (Colaborador / Asistente):
  - Usuario registrado convocado a reuniones institucionales.
  - Consulta exclusivamente sus reuniones convocadas (/api/eventos/mis-eventos).
  - Registro autónomo de asistencia escaneando el código QR del evento desde la app.

* Invitado:
  - Persona externa sin cuenta registrada previamente en el sistema.
  - Registro de asistencia con Nombre y Cédula en reuniones abiertas.
  - Creación automática de cuenta temporal bajo el rol 'Invitado'.


4. REGLAS DE NEGOCIO Y VALIDACIONES
----------------------------------------------------------------------
a) Gestión de Eventos / Reuniones:
   - Anticipación mínima: Los eventos deben crearse con al menos 30 minutos 
     de anticipación respecto a la hora actual.
   - Validación de duplicidad: No se permite crear eventos con el mismo 
     nombre, fecha y hora.
   - Bloqueo de integridad: No se puede editar ni eliminar un evento si 
     ya cuenta con registros de asistencia.
   - Eliminación en cascada: Al eliminar un evento sin asistencias, se 
     remueven automáticamente sus convocatorias asociadas.

b) Tipos de Reunión:
   - solo_miembros: Exclusivo para usuarios previamente convocados en la 
     tabla Participante. Rechaza invitados externos (HTTP 403).
   - abierta: Permite tanto a miembros convocados como a invitados externos, 
     asociándolos automáticamente al realizar el check-in.

c) Control de Tiempos de Asistencia (Ventana de Check-in):
   - Registro anticipado: Se habilita únicamente 15 minutos antes de la hora fijada.
   - Cierre de registro: El registro se deshabilita automáticamente transcurridas 
     4 horas (240 minutos) desde el inicio.
   - Cálculo de Estado (toleranciaMin, por defecto 20 minutos):
     * Presente: Check-in realizado dentro de la ventana de tolerancia.
     * Tardío: Check-in realizado después de la tolerancia pero dentro de las 4 horas.
     * Ausente: Usuarios convocados que no registraron ingreso (calculado en reporte).

d) Unicidad de Asistencia:
   - Un usuario o invitado solo puede registrar asistencia una única vez por evento. 
     Intentos duplicados responden con HTTP 409 Conflict.

e) Seguridad y Cuentas:
   - Contraseñas con longitud mínima de 5 caracteres, hasheadas con bcryptjs (coste 10).
   - Validación estricta de unicidad en Cédula y Correo electrónico.
   - Bloqueo de autoeliminación: Un administrador no puede eliminar su propia cuenta.


5. MODELO DE DATOS Y RELACIONES (SEQUELIZE / POSTGRESQL)
----------------------------------------------------------------------
* Usuario ('usuarios'):
  - id: INTEGER (PK, auto-incremental)
  - nombre: STRING (obligatorio)
  - cedula: STRING (obligatorio, único)
  - correo: STRING (obligatorio, único)
  - passwordHash: STRING (obligatorio)
  - rol: ENUM ('Administrador', 'Operador', 'Miembro', 'Invitado')
  - createdAt / updatedAt: TIMESTAMP

* Evento ('eventos'):
  - id: INTEGER (PK, auto-incremental)
  - nombre: STRING (obligatorio)
  - fecha: DATEONLY (YYYY-MM-DD)
  - hora: TIME (HH:MM:SS)
  - lugar: STRING (obligatorio)
  - toleranciaMin: INTEGER (por defecto 20)
  - tipoReunion: ENUM ('solo_miembros', 'abierta')
  - codigoQr: TEXT (Data URL base64 de la imagen QR generada)
  - createdAt / updatedAt: TIMESTAMP

* Participante ('participantes'):
  - id: INTEGER (PK, auto-incremental)
  - usuarioId: INTEGER (FK -> Usuario.id)
  - eventoId: INTEGER (FK -> Evento.id)
  - createdAt / updatedAt: TIMESTAMP
  * Relación N a M entre Usuario y Evento.

* Asistencia ('asistencias'):
  - id: INTEGER (PK, auto-incremental)
  - participanteId: INTEGER (FK -> Participante.id, 1:1)
  - horaIngreso: TIMESTAMP (por defecto NOW)
  - metodo: ENUM ('qr', 'manual')
  - estado: ENUM ('presente', 'tardio', 'ausente')
  - createdAt / updatedAt: TIMESTAMP


6. SEGURIDAD, AUTENTICACIÓN Y PROTECCIÓN IDOR/BOLA
----------------------------------------------------------------------
* JWT (JSON Web Tokens):
  - Tokens firmados con JWT_SECRET y expiración de 8 horas.
  - Interceptor HTTP en Flutter añade automáticamente 'Authorization: Bearer <token>'.
  - Si el token expira (HTTP 401), el cliente limpia la sesión y redirige al Login.

* Mitigación de IDOR / BOLA en Check-in QR:
  - El endpoint /api/asistencia/check-in-qr extrae el usuarioId directamente 
    del token validado (req.usuario.id), imposibilitando la suplantación de identidad.

* Rate Limiting:
  - Login: Máximo 10 peticiones cada 15 minutos por IP.
  - Check-in: Máximo 30 peticiones por minuto por IP.


7. CATÁLOGO COMPLETO DE ENDPOINTS DE LA API
----------------------------------------------------------------------

--- AUTENTICACIÓN (/api/auth) ---
* POST /api/auth/login
  - Body: { "correo": "...", "password": "..." }
  - Retorna: { "token": "...", "usuario": { "id", "nombre", "correo", "rol" } }

--- EVENTOS / REUNIONES (/api/eventos) ---
* POST /api/eventos                     [Rol: Operador / Admin]
  - Body: { "nombre", "fecha", "hora", "lugar", "toleranciaMin", "tipoReunion" }
  - Retorna: Evento creado con imagen QR en base64.
* GET /api/eventos                      [Autenticado]
  - Retorna: Listado general de eventos (o eventos convocados si es rol Miembro).
* GET /api/eventos/mis-eventos          [Autenticado]
  - Retorna: Convocatorias exclusivas del usuario conectado.
* PUT /api/eventos/:id                  [Rol: Operador / Admin]
  - Body: Campos a modificar (si no tiene asistencias).
* DELETE /api/eventos/:id               [Rol: Operador / Admin]
  - Elimina el evento si no tiene asistencias registradas.

--- PARTICIPANTES / CONVOCATORIAS (/api/eventos/:id/participantes) ---
* POST /api/eventos/:id/participantes   [Rol: Operador / Admin]
  - Body: { "usuarioId": 2 }
  - Asocia y convoca a un usuario a la reunión.
* GET /api/eventos/:id/participantes    [Autenticado]
  - Retorna: Lista de convocados con datos del usuario y estado de asistencia.

--- ASISTENCIA Y CHECK-IN (/api/asistencia) ---
* POST /api/asistencia/check-in-qr      [Autenticado]
  - Body: { "eventoId": 1 }
  - Check-in por escáner de código QR (identidad extraída del JWT).
* POST /api/asistencia/check-in-invitado [Público]
  - Body: { "eventoId": 1, "nombre": "...", "cedula": "..." }
  - Registro de externos en eventos con tipoReunion 'abierta'.
* POST /api/asistencia/eventos/:id/asistencia-manual [Rol: Operador / Admin]
  - Body: { "usuarioId": 3 } O { "nombre": "...", "cedula": "...", "estadoPersonalizado": "presente" }
* GET /api/asistencia/eventos/:id/reporte [Rol: Admin]
  - Retorna: Métricas totales (presentes, tardíos, ausentes) y listado detallado.

--- USUARIOS (/api/usuarios) ---
* POST /api/usuarios                    [Rol: Admin]
  - Body: { "nombre", "cedula", "correo", "password", "rol" }
* GET /api/usuarios                     [Rol: Admin]
  - Retorna: Listado general de usuarios registrados.
* PUT /api/usuarios/:id                 [Rol: Admin]
  - Body: Datos a actualizar del usuario.
* DELETE /api/usuarios/:id              [Rol: Admin]
  - Elimina usuario (bloqueado para autoeliminación de administradores).
